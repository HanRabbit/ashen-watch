# 全量迁移 UE5 实施方案（草案）

> 草案 v0.1，2026-11-25。待拍板：尚未安装引擎，未改动任何代码。
>
> 范围：把《灰烬守夜》垂直切片整体从 Three.js 浏览器工程迁到 Unreal Engine 5，包括玩法、三层地图、双鬼、界面、存档、两套输入、音频和全部美术。
>
> 文中本项目的数字都是 2026-11-25 在工作区实测的。引擎相关事实来自 Epic 官方文档、公告和论坛，出处见附录 B。标「未核实」的条目留到 M0 核对。

## 1. 结论

迁移可行。参考图与现状的差距里，光照和几何密度两类基本可以交给引擎解决，剩下的是美术资产的制作量。

代价有三项：

1. **不再是浏览器游戏。** PRD 的产品定义是「PC 浏览器 · Three.js」，迁移等于改写这个前提。
2. **渲染层全部作废。** `src/render` 的 18,487 行、34 处着色器注入、离线烘焙工具都带不过去，49 个依赖渲染层的测试文件随之失效。
3. **建筑要重新制作。** 现有建筑是 TypeScript 代码生成的几何加自研着色器，不是可导入的资产。

推荐路线：玩法模拟层原样移植成独立的 C++ 模块，与 TS 版逐步对拍；表现层全部用 UE 原生系统重做。先做环境验证和一个参考机位切片（M0、M3），用实拍和帧时间决定是否铺开。

### 与上一份渲染方案的关系

上一份方案（留在 WebGL2 内做参考机位切片、Blender 烘焙全局光）和本方案追的是同一个目标，两者二选一。

- 能带到 UE 的：Rodin 主角资产、主院改回石板的布局决定、参考机位、色调指标。
- 带不过去的：平面反射、光照贴图烘焙、时间抗锯齿、所有着色器。

如果倾向 UE，上一份方案只做能带过去的部分。

## 2. 得失

| | 得到 | 失去 |
|---|---|---|
| 光照 | 全动态间接光和反射（Lumen），昼夜连续变化不需要烘焙；所有局部灯都能投影（现在只有日/月主光有阴影贴图） | 自研的探针烘焙、窗光传输、湿面反射追踪 |
| 几何 | 逐块石作、崩边、雕饰不再受面数限制（Nanite） | 代码即场景：现在改一个常量就能重排墙体 |
| 大气与后期 | 体积雾、体积云、时间超分、胶片后期链都是现成的 | 已调好的四套昼夜参数要重新标定 |
| 内容 | Megascans 扫描库（2026-11-05 起在 Fab 重新免费）；成熟的动画、布料、粒子、音频工具 | — |
| 交付 | 原生 Windows / macOS 包 | 浏览器即开即玩；最低配置从「能开浏览器」升到「有独显的 PC」 |
| 工程 | — | 热更新式的迭代速度；纯文本、可逐行评审的工程（UE 资产是二进制） |

关于网页版：UE 5.8 没有网页目标平台。5.9 预览版新增了实验性的 WebAssembly + WebGPU 目标，用的是移动端渲染器，目前要求源码编译引擎。按这个定位推断它达不到本次迁移要的画质，未实测。

## 4. 目标架构

### 4.1 引擎版本与平台

用 **UE 5.8.4**。5.8 是 2026 年 6 月发布的正式版，Epic 称它是 UE5 最后一个计划内的大版本。5.9 目前只有预览版，Epic 自己说明它的质检周期比平时短，正式版排在 2027 年。

Epic 文档给出的 macOS 渲染特性支持情况：

| 特性 | Apple Silicon 上的状态 |
|---|---|
| Lumen 软件光追 | M1 及以上，支持 |
| Nanite、虚拟阴影贴图 | M2 及以上，Beta |
| Lumen 硬件光追、MegaLights | M2 及以上，实验性 |
| 时间超分（TSR） | M1 及以上，有额外运行时开销 |

本机是 M3 Max、36 GB 内存、831 GB 可用磁盘，硬件够用。有两个平台问题要在 M0 先解决：

- **系统版本超出文档范围。** 本机是 macOS 27.3 + Xcode 27.2。Epic 文档对 5.8 列的是 Xcode 26.0 到 26.1.1，并注明 26.4 不兼容。论坛上 5.8.1、5.8.2 在 macOS 27 + Xcode 27 下打不出游戏包（编辑器能编），该缺陷（UE-396802）标记为在 5.8.4 修复。但 5.8.4 热修复说明里只列了 iOS 的同类修复，Mac 游戏包是否一并修好要实测。另有一位用户报告 5.8.4 在 macOS 27.2 上安装失败。
- **Windows 包要在 Windows 上打。** 按 Epic 历来的说明，Mac 不能交叉编译 Windows 目标（未对照 5.8 文档再核实）。PRD 的验收平台是 PC，所以需要一台 Windows 机器或一条 Windows 构建流水线，同时用它做画质和性能的终验。Mac 上的 Nanite 和硬件光追还不是正式支持状态，Mac 实拍不能代表 Windows 的最终画面。

### 4.2 工程结构

新建一个仓库，不放在当前仓库里。UE 资产是大体积二进制文件，要走 Git LFS；当前仓库冻结在一个标签上，继续充当玩法规格和对拍基准。

```
AshenWatch.uproject
Source/
  AshenSim/         纯 C++ 模拟层，不引用 UObject
  AshenWatch/       运行时：GameMode、Pawn、镜头、表现 Actor、存档、输入、界面基类
  AshenWatchTests/  对拍测试与功能测试
Content/            资产（Git LFS）
Tools/              Python 编辑器脚本、对拍数据导出
```

逻辑写 C++，蓝图只用于资产装配（控件布局、材质、粒子）。C++ 是文本，能评审，也能由代理直接编写；蓝图是二进制资产，只能通过编辑器改。

### 4.3 模拟层：原样移植

现有架构里「模拟状态只读，网格是它的视图」。这个分层直接保留：`AshenSim` 模块逐文件对应 `src/sim`，继续用固定 1/60 秒步长、自己的圆对盒碰撞、节点图寻路和解析式亮区。

不改用 UE 的角色移动组件、导航网格和 AI 感知，原因有两条：

- 鬼的察觉、绕灯、拍门、错开扑击这些规则是按现有几何模型调出来的，PRD 对路线时长有硬约束（主路单程 30–40 秒）。换物理和寻路等于重新调一遍数值。
- 现有 149 例模拟层测试是这套规则的唯一规格。原样移植才能用它们验证。

移植清单：

| TS 文件 | 行数 | C++ 侧 |
|---|---:|---|
| `config.ts` | 161 | 常量头文件 |
| `state.ts` | 132 | 世界状态结构体，保持可序列化为同一份 JSON |
| `level.ts`、`courtPlan.ts`、`baileyApron.ts`、`northCourt.ts`、`southScarp.ts` | 1,057 | 数据部分由 Node 脚本求值后导出 `level.json`；`supportY`、`regionAt3`、`rampY`、`ceilingY` 等查询函数手工移植 |
| `collision.ts`、`nav.ts` | 446 | 逐函数移植 |
| `sim.ts`、`ghosts.ts`、`windChain.ts` | 1,148 | 逐函数移植 |
| `save.ts`、`session.ts` | 247 | 存档信封与进度管理，底层换成 UE 存档 |

**对拍方法。** 在 TS 的 `step` 外面包一层记录器，跑完现有 149 例测试和无头通关驱动（`tests/driver.ts`），把每一步的输入、步前状态、步后状态和发出的事件写成数据文件。C++ 测试逐条读取：从记录的步前状态出发执行一步，再与记录的步后状态比较。

- 模拟层全程用 `double`，与 JS 的数值类型一致。
- 连续量按容差比较，离散量（阶段、鬼的状态、布尔值）必须完全相等。
- 每一步都从记录的状态出发，不做长程自由运行。两种语言的三角函数末位可能不同，长程运行会把这种差异放大成行为分叉；逐步比较能把问题定位到具体的一步。

### 4.4 表现层：UE 原生重做

| 系统 | 现在 | UE 做法 |
|---|---|---|
| 主循环 | `main.ts` 累加器驱动固定步长，渲染时插值 | 世界子系统做同样的累加与插值 |
| 玩家与鬼 | 网格跟随模拟坐标 | Actor 每帧取插值后的模拟位姿，不使用角色移动组件；UE 碰撞只服务于镜头、脚部 IK 和物理小物件 |
| 镜头 | 越肩跟拍，用模拟层碰撞盒做净空 | 重写为对真实几何做球形扫掠。镜头不属于模拟状态，可以放心换 |
| 输入 | 键鼠与纯鼠标两套，支持改键 | Enhanced Input，两套映射上下文，玩家可改键 |
| 界面 | DOM + CSS | UMG：C++ 基类加控件蓝图。字体随包携带 Noto Serif SC（现在依赖系统字体） |
| 存档 | `localStorage`，版本 3，只留黄昏快照 | UE 存档对象里存同一份 JSON 信封。浏览器旧档不迁移 |
| 画质档 | 电影 / 高 / 低 | 引擎自带的可伸缩性分组 |
| 音频 | Web Audio 合成 | MetaSounds 先复刻现有合成音，之后逐项换成录音素材 |

美术必须贴合模拟层的 665 个墙体盒，否则会出现看不见的墙或能穿过去的墙。做法是把关卡数据在编辑器里生成一层可开关的碰撞盒灰模，美术照着它搭；再加一条自动化测试，按网格采样比较模拟层阻挡和 UE 碰撞。

## 5. 渲染与美术

### 5.1 参考图差距的对应做法

| 参考图里有的 | 现状 | UE 做法 |
|---|---|---|
| 大块石板、深缝、高低差 | 泥砾地嵌碎石，平面加视差贴图 | 逐块石板建模并启用 Nanite；缝里的泥、枯草、落叶用贴花和实例化植被 |
| 积水倒映天空和灯光 | 只有屏幕空间反射，画面外的东西反射不到 | Lumen 反射；硬件光追可用时能反射画面外的月亮和壁灯 |
| 带倒角的大块方石墙，逐块色差 | 小乱石贴图铺在平面上 | 模块化石作套件，逐块几何；雨渍、苔、墙脚潮湿用材质层和贴花 |
| 壁灯在墙面和湿地上的光池、所有物体都有投影 | 局部灯不对道具和角色投影 | 局部灯直接开虚拟阴影贴图。全场只有提灯、壁灯、炉火、两个火盆和若干蜡烛，不需要 MegaLights |
| 背光面有层次 | 一套探针，背光面近乎平涂 | Lumen 全局光 |
| 厚云层、月亮、月晕 | 二维噪声云，呈条状拖丝 | 体积云加天空大气；月亮用方向光和月盘 |
| 远处城堡、松林、分层雾 | 低模山体和锥形树 | 远景网格加指数高度雾、体积雾和局部雾体积 |
| 夜景是中性灰石头加暖光 | 整片偏蓝，亮部不足 | 后期体积里重新标定曝光、调色和 LUT |

验收沿用上一轮测得的参考图指标（显示空间 0–1）：白天地面亮度均值约 0.29、饱和度约 0.13；夜晚全帧均值约 0.17、亮部 95 分位约 0.33、饱和度约 0.30。美术圣经第 7 节的地面亮度区间继续有效。

### 5.2 建筑怎么做

这是工作量最大、质量风险也最大的一块。现有建筑不能直接复用，有三条路：

1. **脚本生成模块套件（推荐作为主线）。** 本机有 Blender 5.2，用 Python 脚本生成哥特模块：方石墙段、扶壁、尖拱窗、垛口、券廊、楼梯。脚本是文本，可以由代理编写和迭代。尺寸直接取自关卡数据，天然贴合碰撞。
2. **生成式主角资产。** 礼拜堂立面、井、壁灯、铁栅门这类特写件继续用 Hyper3D Rodin，按参考图裁片生成。
3. **采购现成套件。** Fab 上有中世纪和哥特风格的模块化套件（含付费）。省时间，但要改尺寸去贴合现有地图，风格也要向美术圣经靠拢。

现有场景可以用 three 自带的 `GLTFExporter` 整体导出一份，只作灰模和比例参考。

### 5.3 角色与敌人

- **守夜人。** Tripo 模型带骨骼和 5 段动画（`walk`、`run`、`standing_relax`、`look_around`、`afraid`），可以导入为骨骼网格。现在的行走是自研的程序化步态（`locomotion.ts` 等），带不过去。UE 侧用引擎的动画系统重做：混合空间或动作匹配、Control Rig 脚部 IK、提灯挂插槽加弹簧、斗篷用布料模拟。Epic 有一套免费的动作匹配示例动画，可以重定向过来（凭记忆，授权与 5.8 兼容性未核实）。
- **灰影与黑影。** 默认阵容里灰影的布条层和溶解效果、黑影的整个身体都是代码生成的。灰影另有你提供的 Tripo FBX，但只带攻击类动作，现在靠代码补呼吸动作。两只都要重新制作（Tripo 灰影可作起点）：生成或建模主体，绑定骨骼，布条用布料或 Niagara 条带，溶解用材质。
- **特效。** 扬尘、火焰、余烬、水花、涟漪、滴水用 Niagara 重做。

### 5.4 性能

PRD 的 1080p / 60 fps 目标保留。Lumen、Nanite 和虚拟阴影贴图同时开启时，这个目标对显卡有要求，具体的最低配置要在目标 Windows 机器上实测后确定。第三方报道 5.8 新增了更轻量的 Lumen 模式（Beta），可以作为低档备选，未在官方页面核实。

## 7. 工具链与协作方式

- **代理如何操作编辑器。** UE 5.8 自带实验性的 MCP 插件：启用 Unreal MCP 和 All Toolsets 两个插件后，在编辑器控制台执行 `ModelContextProtocol.GenerateClientConfig ClaudeCode`，会在工程根目录写出 `.mcp.json`，Claude Code 即可调用编辑器里的工具（关卡、资产、材质、蓝图等）。限制：编辑器必须在本机开着；只监听本机回环地址，没有鉴权；属于实验特性，接口可能变。它不可用时退回 Python 编辑器脚本。
- **代码。** C++ 和 Python 都是文本，照常编写、评审、提交。
- **版本管理。** Git 加 LFS 管 `.uasset` 和 `.umap`。本机还没装 `git-lfs`。GitHub 的 LFS 额度是否够用未核实。
- **自动化验证。**
  - 模拟层：对拍测试，不启动引擎也能跑。
  - 功能：把现有的实走机器人思路搬到 UE 自动化测试，按真实输入走完三层路线和三种修复组合。
  - 画面：固定参考机位出图，用亮度与饱和度统计和参考图比较。统计脚本现在在被 Git 忽略的 `.cache/render-plan/measure.mjs`，要先移进 `tools/` 再用。
- **需要你本人做的事。** 用你的 Epic 账号安装启动器和引擎（我无法登录）；提供或确认 Windows 构建机；采购类决定。

## 9. 风险

1. **本机系统比引擎文档支持的新。** 见 §4.1。M0 不过就要考虑降级 Xcode、换版本或等修复。
2. **Mac 上看到的不是最终画面。** Nanite 是 Beta，硬件光追是实验性。终验必须在 Windows 上做。
3. **美术产能与质量。** 引擎解决的是光照和几何密度的上限，不会自己长出资产。脚本生成和生成式模型在特写下能否达到参考图的质感，要到 M3 才知道。
4. **美术与碰撞对不上。** 靠 §4.4 的灰模层和采样测试控制。
5. **数值对拍出现离散分叉。** 个别阈值判断可能因浮点末位不同而翻转，需要逐例排查。
6. **MCP 插件是实验特性。** 接口可能随热修复变化，要保留 Python 脚本这条退路。
7. **二进制资产。** 无法逐行评审，仓库体积增长快，多个代理并行改同一张关卡会冲突。
8. **最低配置上升、迭代变慢。** 引擎编译、着色器编译和资产烘焙都有等待。
9. **迁移和画质升级同时进行。** 两件事叠在一起容易失控，所以 M2 只用灰模，画质放到 M3 之后。

## 10. 需要你拍板

1. **放弃浏览器交付。** 建议：Three.js 版冻结为规格对照版，不再做画质投入。
2. **目标平台与硬件。** 是否以 Windows PC 为主？你手头有没有带独显的 Windows 机器用于打包和终验？
3. **引擎版本。** 建议 5.8.4。
4. **模拟层策略。** 建议原样移植，不改用 UE 的移动、导航和感知。
5. **建筑来源。** 脚本生成加 Rodin（免费素材为主，耗 Hyper3D 积分），还是采购 Fab 套件？是否有预算？
6. **仓库。** 建议新建仓库并启用 LFS。
7. **上一份 WebGL 渲染方案。** 建议只保留能带到 UE 的部分。
8. **先做 M0 和 M3 再定全量。** 建议这样分两步批准。

## 附录 A：坐标与单位换算

模拟层用米；地面是 x–z 平面，y 向上；朝向 `yaw` 为 0 时面向 +z，增大时转向 +x。UE 用厘米，Z 向上，X 向前，Y 向右。

```
X_ue = z_sim × 100
Y_ue = x_sim × 100
Z_ue = y_sim × 100
Yaw_ue（度）= yaw_sim（弧度）× 180 / π
```

这个映射是轮换三轴，不含镜像，所以地图不会左右翻转。它是推导出来的，M2 用几处地标（门房门、井、礼拜堂正门）核对后才算确认。Three.js 渲染层用的是 `z_render = −z_sim`，从 `GLTFExporter` 导出的参考网格要先按这个关系换回模拟坐标。
